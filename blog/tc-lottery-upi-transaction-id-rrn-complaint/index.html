Payment Evidence

Start with the bank-side reference

After a UPI payment, open the transaction details in the UPI or banking app you used. Save the transaction number or RRN, amount, date, time and payee information exactly as displayed. NPCI’s complaint form uses a 12-digit transaction number or RRN for supported complaint workflows, showing why this reference is important for tracing a payment.

Do not rely only on a cropped success screenshot. A screenshot can be useful, but the underlying transaction detail is stronger because it includes the reference and status that the payment system recognizes.

Payment Evidence

Keep the TC Lottery wallet order separately

The wallet can assign its own deposit or order number. That value is not a replacement for the UPI reference. Save both when available: one links the bank-side transfer, and the other links the wallet-side request. If the live wallet shows pending, failed or completed, record the wording and the time you checked it.

When contacting support, state which reference came from which system. Writing “transaction ID” without saying whether it is the UPI RRN or wallet order can create unnecessary back-and-forth.

Payment Evidence

Pending is different from unauthorized

An intentionally initiated deposit that is debited but not reflected in the wallet is a reconciliation problem. Use the UPI deducted but wallet pending checks to compare bank and wallet states before repeating the transaction.

A payment you did not authorize is a security and banking issue. NPCI’s complaint information says fraudulent, unidentified or unauthorized transactions should be raised with the customer’s respective bank for redressal. Do not wait for a gaming wallet conversation to replace the bank-side complaint process.

Payment Evidence

Evidence to save, evidence to hide

Useful evidence includes the amount, time, UPI reference or RRN, wallet order ID, status text and a masked account identifier. Hide the UPI PIN, OTP, full debit-card number, full bank-account number and any recovery credentials. Support does not need those secrets to identify a transaction.

If a screenshot shows a mobile number or account number, mask most digits before sharing it outside your own records. Keep the original privately if your bank requests it through its authenticated support process.

Payment Evidence

Do not create a second payment for proof

A common mistake is sending a small second amount because someone claims the first transaction cannot be located. That creates a new reference and can make the timeline more confusing. A traceable complaint should start from the original payment details.

If the original transaction shows failed and the bank balance was restored, a second deposit may be a separate decision. If the original remains pending or successful while the wallet disagrees, wait for the relevant resolution route instead of multiplying transactions.

Build a timeline

One clear transaction timeline is better than many screenshots

A strong payment record reads like a short timeline: the wallet order was created, the UPI payment was authorized, the bank assigned a reference, and the wallet later showed a particular status. Put those events in chronological order with timestamps. That makes it easier to see whether the disagreement is between a successful bank transfer and a pending wallet, or whether the bank itself still considers the payment pending.

When the status changes, keep the new state without deleting the earlier record. A pending transaction that later becomes failed or reversed tells a different story from one that remains successful at the bank while the wallet stays unchanged. The final complaint should describe the current state and mention the earlier state only when it helps explain the sequence.

If a bank gives a complaint reference number, preserve it separately from the UPI RRN. They are not interchangeable. The RRN identifies the transaction; the complaint reference identifies the support case. Keeping both prevents a later support conversation from losing the connection between the payment and the action already taken.
